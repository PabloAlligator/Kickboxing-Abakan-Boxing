# Технический отчёт — Sodruzhestvo Control

## 1. Исходная архитектура

Статический одностраничный сайт: `index.html`, один SCSS/CSS bundle и Vanilla JavaScript. Отдельно находились Telegram-бот с собственным `node_modules`, EmailJS-форма и SFTP-конфигурация. Backend, база данных, авторизация и административная система отсутствовали.

## 2. Что удалено

- Telegram-бот, polling, его зависимости и конфигурация;
- публичная форма заявки целиком;
- EmailJS SDK, идентификаторы и обработчики;
- стили формы и два неиспользуемых модальных form-блока;
- SFTP-конфиг из рабочей версии;
- мёртвый JS выбора тренера, связанный с формой.

В исходном архиве присутствовал SFTP-конфиг, а в публичном JS — клиентские идентификаторы EmailJS. Их следует считать раскрытыми и при наличии активных интеграций ротировать. Telegram bot token в коде не хранился.

## 3. Публичный сайт

Визуальная концепция сохранена. Телефон и Telegram остались основными каналами связи. Кнопки тренеров и шапки ведут напрямую в Telegram. Расписание загружается через публичный read-only API из Control; если API недоступен или группы ещё не созданы, сохраняется исходное статическое расписание.

## 4. Новая архитектура

- Express-приложение обслуживает публичный сайт, Control и JSON API;
- Prisma + SQLite, реальные последовательные миграции;
- server-side sessions хранятся через собственный Prisma store;
- закрытый mobile-first интерфейс на Vanilla JavaScript;
- PWA manifest, Service Worker, Web Push и планировщик напоминаний;
- PM2-конфигурация и пример Nginx.

## 5. Prisma-модели

`User`, `Session`, `Athlete`, `TrainingGroup`, `GroupCoach`, `GroupMembership`, `GroupTraining`, `Attendance`, `GroupPayment`, `PersonalClient`, `PersonalTraining`, `ClubTask`, `ExpenseCategory`, `Expense`, `PushSubscription`, `AuditLog`, `AppSetting`.

Деньги хранятся целыми копейками. Для истории посещений и финансов стоят restrict-связи; спортсмены и группы архивируются.

## 6. Общая зона клуба

Оба OWNER имеют равный доступ к спортсменам, группам, занятиям, посещениям, групповым платежам, задачам, расходам, общей статистике, публичной Telegram-ссылке и audit log.

## 7. Приватность персоналок

`PersonalClient` и `PersonalTraining` содержат обязательный `ownerId`. Он всегда берётся из `req.session.user.id`. Получение, создание и изменение выполняются только с серверным фильтром по текущему OWNER.

## 8. Защита между OWNER

ID из URL и произвольный `ownerId` в body не дают доступ к чужим данным. Прямые API-тесты подтверждают `404` при попытке второго OWNER открыть чужого клиента или тренировку. Подставленный `ownerId` при создании игнорируется.

## 9. Групповые финансы

Общая формула: сумма всех `GroupPayment` выбранного месяца минус сумма `Expense`. Несколько платежей спортсмена сохраняются отдельными транзакциями и суммируются.

## 10. Личные персоналки

Статистика строится только для текущего OWNER. Доход считается только по `COMPLETED`. `SCHEDULED` и `CANCELLED` не входят в доход. Персональные суммы не участвуют в общем Dashboard и общей статистике.

## 11. Задачи

Общий список без ответственных. Есть название, срок, комментарий, обычный/важный приоритет, напоминание и статусы активна/выполнена. Задачу можно завершить, вернуть и удалить.

## 12. Расходы

Фактический учёт по дате, сумме, категории и комментарию. Seed создаёт стандартные категории, интерфейс позволяет добавить собственную.

## 13. Web Push

Service Worker принимает push и открывает нужный раздел. Подписки привязаны к OWNER. Серверный минутный планировщик отправляет напоминания персоналок и задач, фиксирует `reminderSentAt` и удаляет протухшие подписки. Для реальной доставки нужны HTTPS и VAPID.

## 14. ENV

См. `.env.example`: `NODE_ENV`, `PORT`, `DATABASE_URL`, `SESSION_SECRET`, `APP_ORIGIN`, четыре переменные первичного seed OWNER, три VAPID-переменные и `PUBLIC_TELEGRAM_URL`.

## 15. Локальный запуск

```bash
npm ci
npm run prisma:generate
npm run db:prepare
npm run prisma:deploy
npm run seed
npm run css:min
npm start
```

## 16. Prisma-команды

- разработка миграций: `npm run prisma:migrate`;
- production: `npm run prisma:deploy`;
- клиент: `npm run prisma:generate`;
- начальные OWNER и категории: `npm run seed`;
- `prisma db push` не используется.

## 17. Production deploy

Настроить `.env`, выполнить команды из README, запустить `pm2 start ecosystem.config.cjs --env production`, затем `pm2 save`. Nginx проксирует на порт приложения и передаёт proxy headers. SSL обязателен для secure cookie и Push API.

## 18. Что протестировано

- чистая подготовка SQLite, migrate deploy и seed;
- login двух OWNER, logout и session fixation protection;
- спортсмен, группа, участие, занятие, посещение;
- несколько групповых платежей и расходы;
- формула общих финансов;
- задачи: создание, завершение и возврат;
- личные клиенты и тренировки обоих OWNER;
- статусы `SCHEDULED`, `COMPLETED`, `CANCELLED`;
- IDOR, подмена ownerId, CSRF и чужой Origin;
- HTTP health, public API, авторизованный Dashboard;
- SCSS build и синтаксис JS.

## 19. npm audit

После обновления rate limiter и безопасных overrides: 0 уязвимостей (`info`, `low`, `moderate`, `high`, `critical` — 0).

## 20. Ограничения и production-шаги

- фактическую Web Push-доставку нужно подтвердить после установки VAPID и HTTPS;
- в текущей среде не была доступна браузерная автоматизация, поэтому нужен финальный ручной визуальный проход на реальном телефоне и desktop;
- пароли OWNER намеренно не хардкодятся и задаются только через окружение при seed;
- публичное расписание начнёт заменять статическое после создания активных публичных групп в Control.
